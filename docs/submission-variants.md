# Three Competing Submission Narratives

Each variant is factually compatible with the current project. None claims production use, external integration, or automated native conformance.

## Variant A — Capability lifecycle

**Tagline:** Human approval creates one exact WebMCP capability—and consumes it after one action.

**Opening:**

Most agent safety demos leave a powerful write tool permanently available and ask the model to wait. Agentic Service Dispatch changes the authority surface itself. Five page-owned WebMCP tools can inspect a fictional service request and create a draft. The commit tool does not exist until a human approves the exact canonical draft. It appears for 120 seconds, accepts only the bound approval ID, commits once, and unregisters itself.

**Best for:** WebMCP Leverage, protocol originality, security clarity.

**Risk:** can sound like infrastructure rather than a user product unless the service-coordinator problem follows immediately.

## Variant B — Operations coordinator

**Tagline:** One prompt turns fragmented service records into a reviewable dispatch—without giving the agent standing write authority.

**Opening:**

Service coordinators move between asset records, prior work, provider qualifications, calendars, prices, and dispatch systems. Agentic Service Dispatch gives an agent five structured page tools to assemble that evidence into a visible draft. The coordinator reviews one complete decision, then grants a short-lived capability for exactly that dispatch. After the action succeeds, the capability disappears.

**Best for:** Potential Impact, persona clarity, economic story.

**Risk:** competes with many booking/search/commerce demos and delays the novel WebMCP mechanism.

## Variant C — Shared browser truth

**Tagline:** The person and agent watch browser authority change together: five tools, six after approval, five after use.

**Opening:**

WebMCP is strongest when the human and agent share a live page, not just an API. Agentic Service Dispatch makes the page's actual getTools result the evidence surface. The count begins at five, human approval registers a sixth exact-draft tool, and one successful invocation revokes it. The audit log and capability panel follow toolchange rather than guessing from application state.

**Best for:** browser-native implementation, Execution, judge demo clarity.

**Risk:** more technical and less emotionally grounded.

## Decision

Choose **Variant A** and immediately ground it with Variant B's coordinator problem. Use Variant C as the “How WebMCP is used” section.

Reasons:

1. The rules break ties on WebMCP Leverage.
2. Dynamic capability registration is the clearest competitive white space found in 30 public examples.
3. The 5 → 6 → 5 visual supports the claim without requiring judges to run the app.
4. The operational scenario remains useful as evidence, but should not be mistaken for the innovation itself.

## Final short description

Agentic Service Dispatch turns human approval into a real browser capability transition. Five native page-owned WebMCP tools inspect a fictional service request, review history, compare qualified providers, check availability, and create a visible draft. The final commit tool is absent until a person approves that exact canonical draft. Approval registers a 120-second, hash-bound, one-time sixth tool that accepts only the approval ID. One successful invocation consumes the authority, unregisters the tool, and returns the live registry from six capabilities to five.

## Final 200-character pitch

Five WebMCP tools prepare a dispatch. Human approval creates a hash-bound sixth tool for one exact action. Commit consumes it, returning the live browser capability surface from 6 to 5.
